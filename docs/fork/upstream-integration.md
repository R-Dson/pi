# Upstream Integration Ledger

Fork-specific integration bookkeeping. Update this file whenever fork work touches files that upstream also owns.

## Purpose

This fork evolves pi's session layer toward incremental append-only session processing with crash-safe recovery, a canonical tool pipeline, and bounded tool outputs, while keeping the upstream-visible patch surface small so merges from upstream `main` stay mechanical and easy. Everything outside the fork's own modules is treated as upstream code and changed only through entries in the table below.

## Decisions Log

Pre-made architectural decisions, with one-line rationales. Do not revisit without updating this ledger.

| Decision | Rationale |
| --- | --- |
| Projection cache skipped | `buildSessionContext` runs only on resume, session switch, and compaction — never per turn — because the agent mutates `state.messages` in memory. No hot path, so no cache. |
| Perf/token/cache baselines deferred | Tests must not use real providers or keys, and the faux provider cannot measure provider cache tokens, so there is nothing trustworthy to baseline against yet. |
| Upstream behavior kept: session file creation deferred until first assistant message | Forcing a flush on user-message commit would create session files for abandoned prompts. |
| Neutral directory naming: new session modules live in `core/sessions/` | Upstream-contribution friendly; does not advertise fork ownership in the path. |
| Incremental-index/projection-cache work folded into session validation | No serialized format changes; file order is the sequence, so correctness is validated before any indexing is added. |
| Full `ExecutionScope` (defer/dispose cleanup registry) skipped | Tools already receive an abort signal and clean up on it; a deferred-cleanup registry has no consumer today. Per-tool `timeoutMs` covers the deadline case. |
| Tool output bounding via coding-agent `afterToolCall` hook (not an agent-loop change) | `AfterToolCallResult.content` fully replaces the finalized result content in `finalizeExecutedToolCall` (packages/agent/src/agent-loop.ts), so bounding needs zero `packages/agent` diff. |
| Golden prompt tests are the phase-7 equivalence baseline (issue #12) | `packages/coding-agent/test/system-prompt.test.ts` (golden describe) and `packages/coding-agent/test/suite/prompt-stable-prefix.test.ts` pin today's system-prompt bytes and per-turn request-prefix stability (systemPrompt, tool order, extend-only messages) with zero src changes. No upstream src files changed. |
| Prompt-section framework and tool-order/schema normalization descoped (issue #12) | The baseline tests prove current assembly is already deterministic and prefix-stable within a session, across turns, and across sessions with identical state — the plan's goal (cache-stable deterministic construction) holds without restructuring. A section framework would add abstraction with no observable benefit. Revisit only if a provider-conversion instability surfaces; the tests are the equivalence gate for any such change. |
| Upstream `build-binaries.yml` disabled on the fork | Fork releases go through `fork-release.yml` (GitHub Packages + standalone tarball); upstream's tag-triggered npm-publish/binary machinery cannot work here (no OIDC/npmjs); the `v*` push trigger is removed in-file (manual dispatch remains), and fork-release tags are pushed by `github.token`, which never triggers workflows anyway |
| Permission `ask` blocks with an actionable reason (no approval UI yet); interactive approval when a consumer needs it | Opt-in policy mode must be deterministic in non-interactive modes (print/RPC); a blocked call with instructions for adjusting `tools.permissions.rules` lets the model relay the fix instead of hanging on a prompt nobody can answer. |
| Policy mode uses default effect `allow` (rules opt calls out, not default-deny) | Flipping the mode with no rules otherwise breaks every session; unmatched calls keep legacy behavior. |
| Profiles apply only in policy mode; legacy mode ignores them entirely | Legacy mode must stay byte-identical to upstream; both visibility filtering and profile resolution gate on the one mode read in `getPermissionSettings()`, so no mode checks scatter elsewhere. |
| User rules override profile presets via layered evaluation, not plain rule prepending | Part 1 precedence is deny > ask > allow regardless of list order, so a prepended profile deny could never be beaten by a user `allow`; layers keep within-list precedence unchanged while making any matching user rule win. |
| Hidden tools stay registered; a stale model call to one returns a terminal "Tool not found" error result | The agent loop resolves tools from `context.tools`, so the call fails before `beforeToolCall` runs — an acceptable terminal error; the tool is never executed. |
| Visibility filtering lives solely in `AgentSession.setActiveToolsByName` | Every path that changes the active tool set (construction, registry refresh, reload, extension `setActiveTools`) funnels through it, so hiding needs exactly one enforcement point. |
| Interrupted-turn recovery appends ordinary toolResult message entries at resume | Plan 2.1 forbids new serialized entry types; appending one terminal error toolResult per dangling final-turn call repairs the turn for strict providers (Anthropic rejects tool_use without tool_result) without rewriting history. |
| Fork publishes rename `@earendil-works/*` to `@r-dson/*` at publish time only (`scripts/fork-publish-github.mjs` stages and rewrites; repo manifests untouched) | Repo manifests stay upstream-identical, so upstream merges never conflict on package names or versions. |
| `npm-shrinkwrap.json` and `install-lock` excluded from fork publishes | The shrinkwrap pins `@earendil-works/*` names that do not exist on npm.pkg.github.com (npm forces it into tarballs); dependency integrity comes from exact version pins in the rewritten fork manifests instead. |
| Standalone install channel derives its dependency manifest mechanically from coding-agent's (`scripts/fork-standalone-package.mjs` drops `@earendil-works/*` entries, copies the rest verbatim) | No curated dependency list to keep in sync; the release bundle already inlines all workspace packages, so only public-npm dependencies remain. |
| Hidden thinking renders a live latest-run preview while streaming and a one-line `Thought for Ns` marker when finished (issue #30) | Hidden thinking previously showed only a static `Thinking...` label per run; showing the newest run's first ~120 chars signals liveness while transcripts stay compact. Display-only: no request, session, or settings changes; full text stays reachable via the existing `app.thinking.toggle` expansion. |
| Runtime traffic policy: user-configured provider APIs (provider-required headers only) + explicit user actions; zero pi.dev requests, zero telemetry pings (issue #32) | The fork phones home for nothing: install/version pings, the pi.dev catalog overlay, app-identification attribution headers, automatic startup update checks, and the analytics/tracking settings are all deleted rather than flagged off. No version check or banner is reintroduced; the update command runs only when the user asks. |
| Compaction/branch-summary summarizer calls replay the byte-exact prior request prefix plus one appended instruction turn (issue #40; DSH-derived) | The old standalone summarizer request (serialized `<conversation>` blob, dedicated system prompt, no tools) was a full cache miss on the entire context at the moment it is largest; replaying the agent's real system prompt, full tool list (unfiltered), and converted history lets the provider prefix cache cover the call. The summarizer persona, checkpoint format instructions (format body byte-identical), `previousSummary`, and `customInstructions` fold into the appended user turn. The split-turn turn-prefix summary keeps the standalone serialized shape (it summarizes a fragment, not a replayable request). |
| Update compactions replay the checkpoint message (cache plan phase A review fix) | Since the previous compaction, every regular request begins with the checkpoint message; the replay list is headed by the same projected message so the prefix matches from message 0, while `messagesToSummarize` keeps only new messages so summary semantics are unchanged |
| Replay requests inherit provider caching; standalone summary requests still opt out (cache plan phase A review fix) | `completeSummarization` takes `cacheOptOut` (default true); replaying callers pass false so breakpoints and routing match regular requests, split-turn/standalone callers keep the old opt-out |
| Prefix violations are surfaced with attribution, not raised (issue #41, cache plan phase B; deliberate DSH divergence) | DSH errors on transcript mutation because its extension model forbids it; pi's extension API intentionally allows `transformContext`, so the fork observes every provider-bound request at an AgentSession streamFn wrapper (one layer over the constructed streamFn, covering regular turns, retries, and the phase-A replaying compaction/branch-summary calls), attributes each change to the announcing subsystem or as `unexpected-*`, counts by cause in `SessionStats.prefixInvalidationsByCause`, and emits one `prefix_invalidated` diagnostic event only for unannounced changes. The compaction replay request is NOT append-only relative to the prior regular request (it swaps the trailing user turn for the summarizer instruction; the split-turn turn-prefix summary is a standalone context), so the compact flow announces "compaction" before the summarizer call as well as at the state reset. Announced expectations stay armed until the next stable request — not strictly one-shot — so multi-request flows (split-turn compaction issues two diverging summarizer requests) attribute every call, and an abandoned announcement cannot leak past the next normal turn |
| Per-request cache usage is attributed by request kind at the same streamFn wrapper, not derived from session entries (issue #42, cache plan phase C) | The wrapper already sees every provider request, so usage attribution has one observation point: a one-shot retry marker wins over an active summarizer-flow kind window (`compaction`/`branch-summary`), everything else is a `turn`. `retry` covers the three repeat paths that exist: the agent auto-retry continuation (`_prepareRetry`), the overflow compact-and-retry replay (`_runAutoCompaction` willRetry), and summarizer retries (`RetryCallbacks.onRetryAttemptStart` fires immediately before the re-issued call — a failed summarizer attempt itself stays under its flow's kind). The agent is idle while summarizer flows run, so a window cannot capture unrelated turns; kind attribution is deliberately separate from the phase-B expectation latch so the first regular turn after compaction is a `turn` (its rebuild miss is an invalidation, not summarizer usage). Aggregates are in-memory run-scoped (`SessionStats.cacheUsageByKind`) because the session log must not carry high-frequency per-request telemetry. The kind union carries only kinds a flow produces today; kinds are added when producers exist |
| Upstream's installer-managed update subsystem not ported (upstream 4af9d21d3) | It stages releases fetched from `pi.dev/api/installer/releases` and depends on the deleted `utils/version-check.ts`/`utils/pi-user-agent.ts`; both violate the zero-pi.dev-traffic policy (issue #32) and no fork install is ever a managed install (GitHub Releases channel only, `PI_MANAGED_INSTALL_ROOT` never set). On syncs, drop the subsystem (package-manager-cli.ts managed block, main.ts `cleanupManagedInstall` wiring, its tests, and the `docs/packages.md` managed sentence) the same way the telemetry files are re-deleted. |
| Auto-discovered extensions and skills sort by resolved path at collection (issue #49; DSH parity) | Tool and skills order sits at the front of the request prefix, so readdir-order enumeration (filesystem-dependent: ext4 htree re-bucketing, cross-machine restarts) reorders tools/skills after a restart and busts the provider cache for the whole conversation; lexicographic path order is machine-independent (DSH's deterministic default). Settings-declared order (packages array, settings entries), package manifests, builtin order, and the `toResolvedPaths` precedence ranks are untouched — collection output only feeds the within-rank order of the already-stable rank sort. One-time reorder on upgrade acknowledged: existing sessions may see a single first-request cache miss after upgrading. |
| Replay summarizer calls carry the session routing id, `agent.sessionId` (issue #51; DSH parity) | The two requests built to replay the warm prefix (compaction and branch-summary summarizers) are exactly the ones that dropped the session's cache-routing key, so on providers with session-scoped routing (OpenAI `prompt_cache_key`, Mistral `x-affinity`) the replay landed outside the regular requests' cache bucket. Forwarding `agent.sessionId` — the value the agent loop spreads into every regular request's options — restores routing affinity; on DeepSeek implicit caching it is inert (DSH sends the exact session id on its compaction call). The id is forwarded, never minted, and the standalone split-turn turn-prefix request deliberately does not get it (it opts out of caching and keeps `completeSummarization`'s throwaway id). |
| blockImages toggles are announced as `settings-change` prefix invalidations (issue #53) | The rewrite is the feature, not a violation: `convertToLlmWithBlockImages` (sdk.ts) reads `settingsManager.getBlockImages()` on every request and replaces images in ALL messages — including already-sent ones — with placeholders (that is how image tokens leave the context), so a mid-session toggle is a deliberate full-prefix rewrite that previously surfaced as an unattributed `unexpected-history-change`. The AgentSession request observer now tracks the last-seen effective value and announces before diffing, so the bust counts under its true cause; the tracked value initializes from the first observed request, and semantics stay simple — value flip ⇒ announcement — while a flip that changes nothing on the wire (no images in history) records nothing because the stable request clears the expectation latch. |
| Prefix-monitor blind spot at the provider layer accepted and documented (issue #53; no code) — superseded by the wire-rewrite seam (issue #56) | The monitor observes requests at the AgentSession streamFn boundary; everything `packages/ai` mutates afterward is invisible to it. Two known rewrites: (a) Anthropic deferred-tools migration — on first-party models with `supportsToolReferences`, extension tools sit in `defer_loading` until first used, then migrate into the immediate list, rewriting the wire tools array and the `tool_reference` blocks in past tool results (one-time per tool, dynamic-tool sessions only, Anthropic's own token-saving feature); (b) auth-mode switch — OAuth adds the "You are Claude Code" system block and renames tools, a silent full bust. Candidate seam: a request-serialization hook in packages/ai. Deferred because that is an upstream-surface change in packages/ai for a one-time-per-trigger class of busts; revisit if dynamic-tool sessions on Anthropic become common. Superseded: the seam row below now reports both rewrites. |
| Key-gated e2e test verifies real cache behavior against a live provider (issue #55; DSH `request-cache.e2e.ts` pattern) | `packages/coding-agent/test/e2e-cache-verification.test.ts` is the only oracle for actual hit behavior (byte-equality and faux-provider tests cannot prove it): it drives a real 3-turn conversation with one tool turn plus a manual compaction against Anthropic, with the system prompt padded past the 1024-token cacheable minimum (run-marker-unique padding so request 1 is always a cold miss) and asserts cacheRead>0 on every response after the first, compaction-kind cache usage >0, the session routing id on the replaying summarizer request, and zero `unexpected-*` prefix invalidations. It self-skips without `ANTHROPIC_API_KEY`/`ANTHROPIC_OAUTH_TOKEN` (repo e2e convention), so CI stays hermetic; running it locally costs a few cents. |
| Provider-layer wire rewrites are reported through an optional packages/ai `onWireRewrite` seam and counted directly, not via the expectation latch (issue #56) | `StreamOptions.onWireRewrite?: (cause: string) => void` is the whole seam (additive, undefined-safe, no per-request allocation beyond the callback reference); `buildBaseOptions` forwards it so `streamSimple`-built requests carry it, and the Anthropic adapter fires `"provider-auth-mode"` when a request's auth mode differs from the observer's previous (first observation initializes silently, like `_lastBlockImages`) and `"provider-deferred-tool-load"` when a request anchors a deferred tool load no earlier request of that observer anchored (the `loadedToolNames` transition in `convertToolResult`, checked against the observer's anchored set). Reading the adapter corrected the issue's mechanism description: placement is marker-anchored, not first-use-migrating — a tool used after its marker stays deferred and its `tool_reference` rides the appended marker message, so the anchor request is the rewrite point. The AgentSession streamFn observer injects the callback into the options it forwards and counts each cause once per request, never on the first observed request; it deliberately does NOT call `expectInvalidation` — the fires land inside the wrapped stream call, after this request's context diff, and these transforms never appear in any later context serialization either (the adapter builds fresh wire structures and never mutates the context), so a latch would be cleared by the next stable request unconsumed and would mis-attribute the next unannounced divergence (the blockImages announce-then-diff pattern does not apply to wire-only rewrites). Adapter transition state (`lastOAuth`, the anchored deferred-tool set) lives in a `WeakMap` keyed on the `onWireRewrite` callback: per-session attribution (the coding-agent monitor injects one stable bound method), tracking dies with the observer, and `StreamOptions.onWireRewrite` documents the stable-callback contract. Adjacent stats gap kept documented: requests whose stream ends via `end()` without a result (the `hasResult` fallback in `lazyStream`'s `forwardStream`) stay uncounted by the cache-usage tracker — every built-in adapter resolves `result()` (the terminal done/error event resolves it), so the gap is reachable only by custom API streams lacking `result()`, and counting them would need an EventStream ended-without-result signal: upstream API surface for a diagnostic. |
| Fork feature placement follows pi's minimal-core rule: extension-first where the public extension API allows, core only with a recorded reason (issue #69) | The extension API already exposes the seams the fork's core features use (`tool_call` block-with-reason, `tool_result` content replacement, `getActiveTools`/`getAllTools`/`setActiveTools`), and `examples/extensions/read-only-mode.ts` proves a read-only review pass needs zero fork core. The output cap and permission policies stay core only because the API lacks settings access (extensions cannot read `tools.permissions`/`tools.maxToolOutputBytes`), has no builtin-extension slot (nothing fork-shipped can be default-on), and builtin-first ordering would check policy before user extensions mutate `event.input` — a security-semantics change that must be decided deliberately (issue #70 tracks the move). Session repair, deterministic ordering, the compaction replay, and the request monitor are core on placement: resume-path and provider-request-path positions extensions cannot reach. |

### Catalog-drift hardening (issue #40 CI fix)

The Cloudflare live catalog dropped its last openai-completions gateway models between CI runs. Two consequences, both fixed on this branch:

- `cloudflare-ai-gateway.ts` pins the `createProvider` generic instead of letting it infer from the generated catalog; an empty API subset no longer breaks the static api entry. Upstream adopted the same pin as the named `CloudflareAIGatewayApi` type (e8c632ef6, 2026-08-25 sync); the fork keeps only the explanatory comment above the type.
- Tests pinning the gateway kimi model (`getModel("cloudflare-ai-gateway", "workers-ai/@cf/moonshotai/kimi-k2.6")`) are guarded with `it.skipIf(!getModel(...))` so they run exactly when the catalog offers the model again; the two `model-runtime-cloudflare-compat` tests guard on `getBuiltinModels` the same way.
- The gateway's default model in `model-resolver.ts` moved to `claude-sonnet-4.5` (present in the current catalog); the resolver test iterates all defaults against the generated catalogs, so a vanished default breaks the build the same way.
