# SoL-Pi research: token-efficiency mechanisms vs this fork

Research notes on NVIDIA's SoL-Pi (site: https://nvlabs.github.io/SoL-Pi/, code: https://github.com/NVlabs/SoL-Pi, MIT), studied 2026-09-11 against this fork at 0.85.5. SoL-Pi is not a fork or patch set: it is a pi extension package (`"pi": { "extensions": ["./src/sol-pi/index.ts"] }`) implementing four opt-in token-efficiency mechanisms, discovered by an automated auto-research pipeline (152 proposed mechanisms, 4 survived validation). Their file:line citations below refer to a shallow clone at HEAD (2026-09-11); ours refer to this repo. All four mechanisms run entirely on pi's public extension API — the same API this fork ships, so the comparison is mechanism-vs-mechanism on one substrate.

## Evaluation claims (their site, not reproduced here)

- EdgeBench (51 held-out long-horizon tasks, 2–12 h, xhigh; the site names GPT-5.6 Sol as one backend and never names the second): ~94% of stock pi's average score, 45–49% fewer tokens, ~1/3 lower cost vs pi; 35–64% fewer tokens and 50–54% lower cost vs model-native harnesses (Codex, Claude Code).
- Terminal-Bench 4 (63 CPU-only tasks): SoL-Pi 15/63 solved at $211.12 (lowest $/solved: $14.07) vs pi 18/63 at $286.45. The capability loss on short tasks is real; the win is on cost per solved task.
- Mechanism-level: Action Fusion oracle found edit/write→command adjacency at 12.3% of cross-turn transitions, 87.7% model uptake, counterfactual −10.8% turns (not a measured rerun). ObservationPack paired EdgeBench A/B: provider bill −23.58%, normalized score +22.92%.
- Swarm trial (20 workers, 120 min): −17.5% cycles, −26.8% cost vs stock-pi swarm — explicitly caveated as one non-randomized trial per condition.

Treat the aggregate numbers as NVIDIA's, obtained with GPT-5.6-class models and their benchmark mix; the mechanism designs are what transfer.

## Mechanism 1: Action Fusion — edit/write + validation command in one call

**Theirs** (`src/sol-pi/extensions/action-fusion/`): re-registers `edit`/`write` via `pi.registerTool` as the built-in definition plus an optional `then_run: { command, timeout? }` parameter. Execution order inside one per-file mutex: run the built-in mutation; on mutation failure throw `[then_run:skipped]` (bash never runs); TOCTOU guard (sha256 the file, `setImmediate` yield, sha256 again — skip the command if it changed); execute `createBashToolDefinition(cwd).execute(...)`; on success append `[then_run:succeeded]\n<output>` to the mutation result; on non-zero exit throw the mutation output plus `[then_run:failed]` (the file keeps the mutation). Their per-file queue is external to pi's mutation queue and only serializes fused ops from their instance (`file-queue.ts:53-56`).

**Ours**: `edit` (`packages/coding-agent/src/core/tools/edit.ts:160-214`) applies edits and returns the diff; `write` is the same shape. The follow-up test/build command is always a separate `bash` call in the next model turn. Every edit→verify cycle therefore costs two full model round-trips (edit result → model → bash call → result → model).

**Delta**: we have zero fusion. This is the simplest mechanism to adopt and the only one their oracle pre-screened with a hard transition statistic (12.3% of cross-turn transitions are mutation→command adjacencies; bash is 85.1% of next actions after mutations).

**Utilization**: implement `then_run` natively on our `edit`/`write` definitions. Owning the tools lets us do better than their external mutex: run the fused bash inside our existing `withFileMutationQueue` slot (`core/tools/file-mutation-queue.ts`), which serializes against all mutation traffic, not just fused calls. Their TOCTOU hash guard is only needed because their queue cannot see non-fused writers; inside our queue it is optional (keep a cheap mtime/size sanity check if desired). Preserve their semantics: mutation failure ⇒ command skipped; command failure ⇒ error result carrying both outputs, file keeps the mutation. Also register the `[then_run:*]` markers so downstream mechanisms (below) can reduce just the log suffix.

## Mechanism 2: ObservationPack — send large observations twice, then placeholder + paged recall

**Theirs** (`src/sol-pi/extensions/observation-pack/`): a `pi.on("context")` projection — stored session history is never edited, only the per-request copy. Eligible results are text-only, non-error `toolResult`s over 10 KiB (excluding EPR receipts). Request 1–2 send the full bytes; request 3+ sends a placeholder: id, tool, original sizes, a retrieve hint, 512 B head + 512 B tail whole-line excerpts. The full text is archived once, content-addressed (`obs_` + sha256(tool, call, text-hash) id, `O_EXCL|O_NOFOLLOW`, 0o600, collision re-verified by size and full sha256). A registered `obs_recall { id, offset? }` tool pages the original back at ≤16 KiB / 400 lines per call with `next_offset`/`eof` headers; iterating offsets reproduces the original bytes exactly. Fail-open on any error (original stays). Decisions go to a JSONL ledger.

**Ours**: truncation happens at capture time. `read` keeps the first 2000 lines / 50 KiB with offset/limit continuation hints (good paged recall for files); `bash` keeps the tail (`core/tools/truncate.ts:168-241`), but the truncation notice embeds the full-output temp path (`core/tools/bash.ts:327-331`) and that temp file holds the complete raw output and is never deleted (`core/tools/output-accumulator.ts`) — the head is recoverable by reading the file back through the paged read tool; recall costs extra tool calls and each page re-truncates, but nothing is destroyed. Grep lines are cut at 500 chars. The loop-level bound (`core/tools/output-bounds.ts`, 200 KiB) spills full text to an artifact file (persisted sessions) and shows head+tail; recall works the same way, through the read tool.

**Delta**: two orthogonal differences. (1) Lifecycle: ours decides once, at capture, what the projected context carries — a large observation then stays in context in full (cache-read priced, but consuming window) until compaction; theirs decide per request, shrinking the projected context once the observation is stale (after 2 sends). (2) Recall: theirs is exact and byte-addressable over a stable, content-addressed archive with a dedicated paging tool; ours routes through the generic read tool over scattered tmp paths, re-truncating per page. Their measured effect (−23.58% bill, +22.92% score in paired A/B) makes this the largest single win.

**Utilization**: adopt the archive-handle-recall lifecycle for bash-class outputs.
- Extend the existing artifact spill (we already write full bash output to `pi-bash-*.log` in tmpdir, `core/bash-executor.ts:69`, and spill >200 KiB results via `output-bounds.ts`) to a session-scoped, content-addressed object store with stable ids, and stop destroying the bash head in `truncateTail` — the projected excerpt can stay tail-weighted, but the archive must hold everything.
- Add the `context` projection with FULL_SENDS=2 then placeholder, and an `obs_recall`-style paging tool (their 16 KiB/400-line page with `next_offset`/`eof` is a proven shape; our `read` tool's offset/limit continuation hints are the in-family precedent).
- Cache interplay (fork-specific): the first placeholder substitution rewrites an earlier message and busts the provider prefix cache from that point — exactly the "cache debt" their OCC accounting prices (`FULL_SENDS=2` means the bust happens once, after which the projection is stable again). Our byte-stable-prefix discipline (`docs/fork/cache-preserving-context-plan.md`) must treat this as a deliberate, accounted rewrite, not a violation: fold the bust cost into the compaction-style economics below rather than forbidding the projection.

## Mechanism 3: Evidence-Preserving Reducer — cheap-model first read of diagnostic logs, receipts only if verifiable

**Theirs** (`src/sol-pi/extensions/evidence-preserving-reducer/`): on `tool_result` for commands matching a diagnostic regex (pytest, cargo, make, ninja, go test, bazel, npm test, ...) with body ≥4 KiB and ≤600 k chars and no secret-looking content: archive the log content-addressed; call a cheaper model (default `openai-codex`/`gpt-5.6-luna`, `maxTokens ≤ 2048`, 90 s timeout, `cacheRetention: "none"`) with the log wrapped in `<untrusted_log>` and instructions to emit only a JSON receipt of ≤12 verbatim quotes. The receipt is accepted only if: schema valid, `source_sha256` matches the archive, status equals the observed exit code, every quote is a byte-for-byte substring of the archived body, a failing log matching failure signals carries at least one fatal/failure evidence item ("missing-failure-evidence" gate), and the receipt is smaller than the source. On acceptance the result is replaced by the receipt (which lists verified quotes with line numbers, quote hashes, and the `source_artifact` path for exact bash readback); on any failure the original result is untouched (fail-open), with journaled fallback reasons.

**Ours**: no observation-routing delegation — the frontier model reads the truncated tail of every test log itself, every time, until compaction. (The model-handoff extension's `switch_model` tool can hand a whole run to a cheaper tier, but there is no second-context subagent and nothing that pre-reads observations.)

**Delta**: no equivalent mechanism exists here (model-handoff switches tiers for whole runs; it does not pre-read observations). This is the most opinionated mechanism (a second model sees the logs; needs a configured route; NVIDIA default is their own stack) but the verification protocol is model-agnostic and is the transferable core: archive first, reduce against the archive, accept only quotes that verify against archived bytes, require failure evidence on failing runs, fail open.

**Utilization**: optional, experiment-tier. The building blocks exist: `details.fullOutputPath` / `pi-bash-*.log` is already produced by our bash executor (the exact hook they consume), and our fork just gained `ctx.modelRegistry.stream()/streamSimple()` extension streaming (2026-09-08 sync), which is a cleaner route than their `registry.complete()` / `getApiKeyAndHeaders()` dual path. Route choice stays user-configured (a locally-served model keeps logs local). Their secret regex is a precaution, not a scanner — if we build this, keep the archive local-only unless a remote route is explicitly configured, and say so.

## Mechanism 4: Online Context Compact — economics-gated compaction at subtask boundaries

**Theirs** (`src/sol-pi/extensions/online-context-compact/`): registers an `update_plan` tool (full-plan replace, 1–128 steps, optional `progress {files_changed, verification, decisions}`); a step newly completing is a boundary. State (request counts, per-boundary intervals, positive context growth, compaction count, cache debt) persists as custom session entries. At `turn_end` on a boundary:

```
writeTokens   = current context tokens (max of provider-reported and estimated)
archiveTokens = max(0, writeTokens − systemPrompt − 20_000 keepRecent)   # what compaction removes
memoTokens    = 1_000                                                     # the summary itself
saving        = archiveTokens − memoTokens
breakeven     = writeTokens × (cacheWriteReadRatio − 1) / saving          # requests to repay the rewrite
expected      = min(1 + mean(requests/boundary) × remainingSteps,
                    (window − context) / avgGrowth)
compact ⟺ saving > 0 ∧ (context ≥ window − 16_384                         # window protection
                        ∨ breakeven ≤ expected)                            # economics
```

with first-compaction leniency (`expected × 2`), a ×1.5 margin plus carried-debt gate for subsequent compactions, and `cacheWriteReadRatio` defaulting to 12.5 (GPT-5.6 Sol cache-write/read pricing; 0 = free writes). Steering input or `CORRECTION:` resets the epoch. Choreography: at the boundary `ctx.abort()`; at `agent_settled` + idle, call pi's native `ctx.compact()` with custom instructions ("Preserve completed work, verification results, important decisions, and remaining work"), block tree navigation during flight, then send a hidden `triggerTurn` message instructing the model to rebuild the plan, and hold the settlement barrier open until that continuation settles — so print/JSON mode finishes compact-and-continue inside one process. A native-feasibility precheck via public `findCutPoint` cancels no-op compactions.

**Ours**: compaction is purely reactive, with two trigger hooks. Mid-run, before each next assistant response, an estimate-based check (`_compactBeforeNextAssistantResponse`, `core/agent-session.ts:642-659`, wired through `packages/agent/src/agent-loop.ts:176-190`) compacts when the estimate crosses `contextWindow − 16_384` (`shouldCompact`, `core/compaction/compaction.ts:236-239`) and the same run continues with the compacted context — so compact-and-continue already works in headless modes. Post-run and before each new prompt, a usage-based check (`_checkCompaction`, `core/agent-session.ts:2303,2403`) compacts after the fact; overflow recovery retries the aborted turn once. Compaction keeps ~20 k recent tokens, cuts at valid turn boundaries, and generates the structured checkpoint summary (plus file-ops lists, split-turn prefix handling). No economic model, no notion of subtask boundaries, and no post-compaction prompt to reconstruct the plan — the mid-run hook continues silently between assistant responses. Constants match theirs (reserve 16 384, keep 20 000 — they hardcode ours).

**Delta**: trigger semantics (semantic boundary + economics vs window pressure only). The interesting part is the economic model: a compaction rewrites the whole context (cache-write premium ≈ ratio−1 per token), so compacting early only pays if enough remaining requests amortize the rewrite; their formula computes exactly that breakeven.

**Utilization**: adopt boundary-triggered, economics-gated compaction on top of our native compaction, in three parts:
1. Plan/progress tracking (`update_plan`-style tool with progress evidence fields) to get boundaries. Cheap; independently useful for long tasks.
2. The breakeven decision — with a fork improvement: derive `cacheWriteReadRatio` per model from our own cost metadata (`Model.cost.cacheWrite / cost.cacheRead`, populated from `packages/ai/src/providers/data/*.json`) instead of a hardcoded 12.5, degrading to their default when pricing is unknown. This also makes the formula correct for providers and models whose cache-write premium differs from GPT-5.6 Sol's, and for local/free-cache setups (ratio 0 ⇒ compaction economics collapse to plain token savings).
3. Post-compaction plan-rebuild reminder (their hidden `triggerTurn` message). Our mid-run compaction continues the run, but nothing prompts the model to reconstruct its plan after the context shrinks; their reminder is the cheap fix. Their settlement-barrier machinery is not needed — it exists to make compact-and-continue work in one process, which our mid-run hook already does.

This composes with `docs/fork/cache-preserving-context-plan.md` rather than competing: phase A of that plan makes the summarizer call itself nearly a cache hit (prefix-replaying summary); OCC decides *when* to compact so the rewrite happens at the cheapest moment (boundary, economics open) instead of at maximum window pressure. The two multiply: cheaper per compaction and better-timed compactions. Sequencing note: land the prefix-replaying summarizer first — it changes the `writeTokens × (ratio−1)` cost term OCC depends on.

## What to adopt, in priority order

1. **Action Fusion** (`then_run` on edit/write, native). Smallest diff, highest certainty, no new infrastructure, no model-behavior risk beyond an optional parameter. Fits this repo's own mandated workflow (run-tests-after-edit loops). Expected effect: one model round-trip saved per edit→verify cycle.
2. **Observation lifecycle** (archive + handle + FULL_SENDS=2 projection + paged recall for bash-class outputs). Largest measured effect (−23.58% bill in their A/B). The win is the projection lifecycle, not recall — our bash heads are already recoverable via the temp-file path; what we lack is stale observations leaving the projected context before compaction, stable content-addressed handles, and a dedicated paging tool. Must be integrated with the prefix-stability monitor from the cache plan (accounted rewrite, not violation). Tuning datapoint: their sweep winner used 2,048/1,536-byte head/tail excerpts; the release ships 512/512.
3. **OCC economics + boundary compaction** on top of (and after) the prefix-replaying summarizer. Per-model cache ratio from our cost metadata is a concrete improvement over their design.
4. **EPR** as an opt-in experiment; transferable core is the verification protocol (quote-inclusion against archived source, failure-evidence gate, receipt-smaller gate, fail-open). Privacy-sensitive: second model sees logs; keep local-route support first-class.
5. **Their validation methodology**, not just their outputs: capability floors as acceptance gates, fail-before/pass-after environments built from real issue→PR pairs (495 of their 535 training envs were exactly that — this fork has its own issue/PR history to mine), held-out sets that never feed repair. `packages/evals` is the place to build this. Their 152→4 survival rate is the argument: most efficiency ideas fail a capability floor, so any port we do needs the same gate, and the gate needs to exist before the port.

## Integration decisions: core vs extension

Pi's philosophy, as this fork has recorded it in practice: core owns correctness contracts and data paths (agent loop, session persistence, compaction, the mutation queue, truncation bounds, context assembly); extensions own policy, opinion, model routing, and trust decisions (upstream's stated position on permission flows, which the fork's issue #70 removal of core permission mode codified). The fork adds its own constraint: every core divergence from upstream pays permanent upstream-sync rent, so it must be correctness-critical or trivially upstreamable, and it gets a ledger row. Apply two tests to each mechanism: (1) can an extension implement it *correctly* from outside, using public APIs only? (2) is it universal (no user decision required), or policy?

**Core (native implementation, ledger-recorded divergence):**

- **`then_run` on edit/write.** Fails test (1): a fused mutation executed by an extension cannot enter `withFileMutationQueue`, so it races plain `edit`/`write` calls — SoL-Pi's own docs concede their external queue covers only their fused ops, and their TOCTOU sha256 guard is a workaround for exactly this. In core the fused bash runs inside the mutation-queue slot and the guard becomes unnecessary. The parameter and its `[then_run:*]` result markers are part of the tool contract other mechanisms match on; extension-invented markers inside core tool results would be fragile. Universal: an optional parameter, no policy.
- **Observation archive with stable handles + paged recall.** This is the observation data path — core already owns truncation and artifact spill, and the session-scoped store is persistence-layer infrastructure (it extends what `pi-bash-*.log` and `output-bounds.ts` spilling already do ad hoc). Extensions (a reducer, anything) build on it. It also fixes the ergonomics gap: recall via stable handle + dedicated paging instead of a tmp path embedded in a human-readable notice. Shipped minimal form (2026-09-11): truncated shell outputs spill to `<sessionDir>/artifacts/<sessionId>/` with the path as the handle and the `read` tool as the paging path; content-addressed names and a dedicated recall tool are deferred until the projection extension needs stable ids.
- **Two small exports:** the effective compaction settings getter (SoL-Pi had to hardcode `keepRecentTokens = 20 000` because pi does not publish it) and a per-model cache write/read ratio helper in pi-ai (data already in `Model.cost`). Both are trivially upstreamable, near-zero sync rent.

**First-party extensions (in-repo under `packages/coding-agent/src/extensions/`, default off — the permission-policies / model-handoff pattern):**

- **Observation projection (FULL_SENDS=2 → placeholder).** Implementable correctly from outside via `on("context")` (SoL-Pi proves it). It is context policy with tunable constants, not a correctness contract. One fork-specific requirement: the prefix-stability monitor (cache plan phase B) must be taught to attribute this extension's rewrite as a known, accounted cache debt rather than a violation.
- **Evidence-Preserving Reducer.** Pure policy and trust: which (if any) second model sees logs, at what cost, under what privacy constraints. Never default-on. Depends on the core archive for its untruncated source and hash; routes through `ctx.modelRegistry` with the user's configured model.
- **Online Context Compact (plan tool + boundary trigger + economics + post-compaction reminder).** The `update_plan` tool is workflow opinion — upstream pi deliberately ships no plan tool, and adding one to core is a large divergence for low rent. The economics formula is pure computation and lives naturally with the trigger. Uses the two core exports above. The settlement barrier is unnecessary for us (mid-run compact-and-continue already exists in core).

**Repo infrastructure, not shipped code:** the validation gate — capability floors, fail-before/pass-after environments mined from our own issue→PR history, held-out sets — belongs in `packages/evals` and should exist before any of the above is trusted.

## Compatibility notes

- SoL-Pi targets `@earendil-works/pi-coding-agent` 0.84.2 (type-checks against 0.81.1). This fork is 0.85.5 and in-repo package names are unchanged, so the entire public surface they use exists here: verified `findCutPoint`, `estimateTokens`, `buildSessionContext` exports in `packages/coding-agent/src/index.ts:40,42,238`; `registerTool`, `on("context")`, `on("tool_result")`, `on("turn_end")`, `on("agent_settled")`, `ctx.compact()`, `ctx.abort()`, `ctx.isIdle()`, `pi.appendEntry`, `pi.sendMessage({triggerTurn})` all present in `core/extensions/types.ts`; `details.fullOutputPath` / `pi-bash-*.log` produced by `core/tools/bash.ts` + `core/tools/output-accumulator.ts` for the model-facing tool (and separately by `core/bash-executor.ts` for the user `!`-bash path).
- Two of their pinned behaviors need re-verification on 0.85.5 before porting OCC as-is: `sendMessage()` starting turns synchronously (their settlement barrier depends on it; our `ExtensionAPI.sendMessage` still returns `void`, `types.ts:1392-1395`) and `compact()` aborting the active agent. Their docs flag third-party `agent_settled` handlers as unverified against this pattern.
- Published-fork caveat: the Fork Release workflow publishes under `@r-dson/*`, while SoL-Pi's peer dependencies and imports reference `@earendil-works/*`. Installing SoL-Pi into a published fork build would resolve those against the npm upstream package — a second, different pi runtime inside the extension. Trying SoL-Pi against a local workspace checkout (names match in-repo) is the supported way to evaluate it here; do not recommend `pi install git:github.com/NVlabs/SoL-Pi` to fork-release users without resolving the naming split.
- Their archives persist after session end (no GC); per-session isolation, no migration. If we adopt archive-based mechanisms, decide retention explicitly.

## Caveats on their results

- Combined harness retains ~94% of stock pi's EdgeBench score; per-mechanism tolerated losses accumulate. TB4 shows the short-task regime cost (15/63 vs 18/63 solved).
- Action Fusion savings are counterfactual (adjacency analysis), not measured reruns; ObservationPack numbers are a paired A/B on 11 tasks × 2 arms.
- The swarm result is one non-randomized trial per condition, with repair pauses in the SoL-Pi arm.
- Default reducer route (`openai-codex`/`gpt-5.6-luna`) is NVIDIA-stack-specific; economics default (12.5) is GPT-5.6 Sol OpenAI pricing, wrong for other providers — our per-model ratio derivation addresses this.
